Task #21 — MaryV2 Full Operational Certification

Tasks #15–#20 have repaired several classes of runtime/test divergence. We now need to determine whether MaryV2 is genuinely functioning as one integrated computational character in production.

This is not primarily a coding task.

Do not begin by changing code.

Do not assume a subsystem works because:

* a unit test passes
* an integration test passes
* a class exists
* a status endpoint says enabled
* a subsystem can be constructed
* documentation says it is implemented

The goal is empirical operational proof.

Certification standard

For each major MaryV2 capability, distinguish:

* LIVE VERIFIED
* LIVE VERIFIED WITH LIMITATIONS
* TEST VERIFIED ONLY
* IMPLEMENTED BUT NOT EXERCISED
* PARTIAL
* FAILED
* UNKNOWN

The final claim PASS — COHERENT OPERATIONAL SYSTEM is allowed only when the major intended runtime loops actually complete.

⸻

1. Canonical identity and runtime

Prove live that there is:

* one canonical Mary identity
* one canonical MaryApplication/Core authority
* no competing runtime state
* surfaces are clients
* providers are replaceable cognition
* capability nodes are replaceable capability providers

Exercise production Mobile/Core rather than inferring solely from source.

Perform several small authenticated creator turns.

Prove the actual sequence:

surface
→ Core

→ cognition/provider
→ response
→ growth/experience
→ learning candidates where appropriate

3. Memory + Experience Evolution

Repeat the controlled production learning experiment after Task #17.

Prove independently:

Immediate context

Same-conversation temporary recall.

Selective non-learning

Incidental temporary information is not blindly promoted.

Explicit preference evidence

Authenticated creator preference creates appropriate structured candidate/evidence.

Governance

Candidate is promoted, deferred, reviewed, or blocked for an explainable reason.

Reinforcement

Appropriate repeated evidence can advance through governance.

Persistence

Promoted state survives a fresh conversation and other intended persistence boundaries.

Retrieval

New conversation retrieves relevant durable state.

Behavioral influence

Mary changes a later response because of learned evidence without the preference being repeated in that turn.

Corrective feedback

Negative/corrective creator feedback affects later comparable behavior.

Confirm throughout that CharacterSourcebook remains unchanged.

This subsystem does not pass merely because candidates now appear. The entire intended learning loop must be demonstrated.

2. capture bounded evidence
3. identify exact ownership/path
4. classify the defect

Produce follow-up work items unless the correction is trivial and clearly within an already-approved certification repair scope.

We want certification evidence to remain trustworthy.
